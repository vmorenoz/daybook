## Daybook MCP

- Use `daybook` to preserve and resume project work: tasks, plans, progress, agreements, and blockers. Skip trivial questions unless the user requests tracking.
- Present tool results in concise, plain language, prioritizing useful titles, descriptions, outcomes, and next steps over IDs or relationship keys. Make actions and important consequences clear. Keep identifiers internal; provide technical details and traceability only when explicitly requested.
- Before starting project work, read `project_id` from the `daybook` block in the project's root `AGENTS.md`. Accept an existing legacy `alba-cortex`/`vimo-cortex` block or `proyecto_id` key as the same binding; never initialize a duplicate because it uses an old name. Reuse this ID as `project_id` in project-scoped MCP calls. Ask the user if stored IDs conflict.
- If neither key exists, tell the user: "This project has not been initialized in Daybook." Offer to create a new project with `create_project`, or use `list_projects` so they can select an existing one. Do not create or link a project automatically: wait for their choice. Store the chosen ID as `project_id` in that block without replacing other instructions.
- Store `work_versioning: track` or `work_versioning: ignore` in the same block. Accept legacy `versionar`/`excluir` as equivalent decisions. In a Git repository, before first using `.work/` without a stored decision, ask once whether to track or exclude it and persist the answer. Do not ask again or change it unless requested. Without Git, ask when versioning becomes relevant.
- For `track`, add no exclusions; for `ignore`, add `/.work/` to the project's `.gitignore` without changing other rules. If files are already tracked or rules conflict, report it without deleting or untracking anything automatically. Do not ignore an existing `AGENTS.md` to hide its metadata.
- Keep only useful, on-demand working documents in the project's `.work/`: `plans/`, `decisions/`, `attachments/`, and `evidence/`. Reuse existing legacy folders (`planes/`, `decisiones/`, `anexos/`, `evidencias/`) rather than renaming or duplicating documents. Create only needed folders; no configuration, IDs, session reports, empty documents, or redundant evidence. Small tasks need no document.
- When resuming, call `get_active_context`; use `get_details` only as needed. Discover the available tool schemas before calling them.
- Use `create_item` for standalone tasks or structured work, `add_note` for meaningful progress, and `update_item` for the actual status. Always pass `project_id`; never invent progress, evidence, or authorization.
- Mark finished work as `completed` without requiring evidence. Query `list_history` explicitly and use `reopen_item` to preserve the same ID.
- Delete only at the user's request: `delete_project` requires confirmation and cascades through all project data in Daybook; `delete_task` also requires confirmation. Set `confirm: true` only after receiving it. `delete_plan` requires deleting all phases and tasks first; `delete_phase` requires deleting all its tasks, including closed ones. Never delete `.work/` documents as part of these operations: the user decides whether and when to keep or remove them.
- Create, read, and edit documents using file tools; link their absolute paths in the project's `.work/` through the MCP when appropriate. Documents stay in the project, not in Daybook's central storage. The MCP stores references and never returns document contents. Do not record unnecessary sensitive information.
